# Spell IDE Map — how the missing things are enumerated, ordered and built (2026-09-19)

Owner, 2026-09-19: *"there are dozens, if not hundreds of things that we need to work on
... how do you enumerate over them, organize them, and somehow help me work through what
an IDE looks like? How do we choose what our animation should be (from existing of
course), how many phases, add emitters, etc — the big issue is that nothing here is really
easy to understand."*

This document is the answer, and it is meant to be re-read and re-generated, not read
once. The Spell Creator IDE (`SPELL_CREATOR_IDE.md`) and the Sketch (`SPELL_SKETCH.md`)
describe what is BUILT; this one holds the METHOD for finding what is not, the ORDER to
build it in, and the SPINE the whole tool hangs on so that a new author can understand
it. §1 is the method, §2 the spine, §3 the inventory, §4 the task walk, §5 the next
slices, §6 what landed today and how it was found.

## 0. The short version

There is no need to guess at "hundreds of things". A 1.12 spell's visual is a FINITE
schema — Spell.dbc → SpellVisual → SpellVisualKit → SpellVisualEffectName → M2 → BLP,
plus sound — and every field of it is a row in a table with four columns: *does the
runtime play it, can the IDE show it, can the IDE set it, does it survive export*. That
table (§3) is the enumeration; it has about 240 rows today. It is ORDERED by two things
that are also not opinions: how often Blizzard's own 1,977 visuals use each field (§1.2,
regenerated by a script) and which author intents (§4) it blocks. And it is ORGANIZED for
the author by one spine (§2): the spell's timeline of parts, each part owning what the
body does, what plays where, and how big — with every "add" being a copy from a real
spell, never a number typed from memory.

## 1. The four enumerations (the method)

Each has a source of truth outside anyone's memory and a way to regenerate it.

### 1.1 The schema walk — what CAN exist

Walk the format, field by field, and write a row for each. Sources: the client's own
readers (`Formats/SpellVisualCatalog.cs` for the DBC chain, `Formats/M2Reader.cs` and
`Creator/M2*Parser.cs` for the model, `SketchWriter.cs` for what the compiler emits) and
the byte-verified layouts in `docs/current/spells/BENILLA_SPELL_SYSTEM_TRACE.md`. This is
mechanical and complete: when the row count stops growing, the enumeration is done. §3 is
this walk.

### 1.2 The census — what real spells USE (the order)

Not every field matters equally, and the data says which. `python
tools/spellvis/spell_visual_census.py` (read-only, over the local archives) reports, over
the **1,977 SpellVisual rows that real spells reference** and the **1,463 kits they
reach**:

| Fact | Count | So |
|---|---|---|
| Visuals with a cast kit / impact kit / precast / state / channel | 68% / 61% / 38% / 35% / 6% | Cast and impact are the tool's centre; channel is a corner |
| Most common anatomies | cast+impact 13%, precast+cast+impact 13%, impact only 10%, state only 9%, cast only 7% | The five presets in Anatomy cover ~60% of real spells |
| Visuals with a missile model | 10% (203; 68 distinct models) | Missiles are a tenth of the game, not the default case |
| Kits with a caster animation | 49% (84 distinct ids; top: 54 SpellCastOmni, 53 SpellCastDirected, 52 ReadySpellOmni, 124 ChannelCastDirected, 123 UseStandingLoop) | Half of all kits animate the body — the picker had to exist |
| Kits with a sound | 67% | Sound is more common than animation |
| Slot use per kit | Base 29%, Chest 20%, LeftHand 20%, RightHand 19%, Head 13%, Breath 4%, Special1..3 1%/0%/0% | Five slots matter; Breath is rare; Specials are near-dead |
| Models per kit | 0: 375, 1: 775, 2: 227, 3: 56, 4+: 30 | One or two models is the norm; the tree never needs to be deep |
| Effect scale ≠ 1 | 409 of 1,549 slot fills (26%) | The Composition scale dial is used a quarter of the time |
| Kit extras real spells set | CharProcs on 226 kits (type 1 = 79, 0 = 41, 8 = 27, 13 = 17, 11 = 15, 12 = 14, 14 = 11 ...), camera shake 51, world effect 30 | The runtime honours proc types 0 (chain beam) and 9 (area shards) — the rest are engine gaps before they are IDE gaps |

And over the **1,699 particle emitters in 438 spell models** (`dumps/spell-emitter-census.csv`,
written by the lab):

| Fact | Count | So |
|---|---|---|
| Shape | Plane 868, Sphere 811, Spline 20 | Two shapes; spline is a footnote |
| Blend | additive (4) 1,430, alpha (2) 244, opaque/key 25 | Additive is the default worth defaulting to |
| Head / tail / both | 1,140 / 513 / 46 | Tails are a third of the game |
| Emitters with an ANIMATED scalar track | 680 (40%) | Keyframe editing is not a nicety: nearly half of all emitters ramp |
| Multi-key enable (burst windows) | 855 (50%) | Same: a "when is it on" timeline is half the data |
| Riding an animated bone (bone motion / bone spin) | 535 / 164 | The frame chain in SPELL_CREATOR_IDE §1 is the common case |
| Negative speed | 192 | The sign law matters for one emitter in nine |
| Gravity / drag / sprite spin / tumble | 304 / 504 / 700 / 69 | Spin is common, tumble rare |
| Geometry-model / recursion emitters | 44 / 13 | Rare, but they draw whole M2s per particle — an IDE that ignores them shows nothing for those 44 |

Re-run the script when the data changes; the numbers above are the 2026-09-19 baseline.

### 1.3 The task walk — what an author WANTS

Write the sentences an author actually says ("make it red", "start it from the hand",
"make the caster swing two-handed", "give the missile a trail like Fireball's") and for
each one the click path in the IDE. A sentence with no click path is a gap, and a sentence
whose click path is four panels long is a usability gap. §4 is the current list. This is
the enumeration that the owner does by playing with the tool for days; writing it down is
what stops it being rediscovered.

### 1.4 The round trip — the objective test

For any spell in Spell.dbc: load it into the IDE, export the session, let the Completer
build, compare the result against the original rows and bytes. Every field that does not
survive is a gap, listed automatically, and the count of spells that survive losslessly
is a METRIC. Not built yet (§5, slice R); it is the enumeration that would make §3's
"Export" column a fact rather than a reading of the code.

## 2. The spine (how the IDE is organized)

The anatomy IS the organization. A `SpellVisual` row is a set of independent parts and
the game fires every part that is filled (`SpellVisualCatalog.cs`: "every populated slot
on a reached row fires; the stage selects LIFETIME POLICY only"). So the tool's root is
the spell's TIMELINE of parts, in the order a player experiences them, and everything
else hangs under one part:

```
SPELL  (name · icon · school · what it DOES — the Completer's half)
 └─ TIMELINE                     Precast → Cast → Missile → Impact → Channel / State / Area
     each PART owns:              in the plan?  ·  body does (animation)  ·  sound  ·  lifetime policy
      └─ SLOTS (where on the body) Head · Chest · Base · Left hand · Right hand · Breath  (+3 near-dead Specials)
          each SLOT holds:        one effect MODEL  ·  scale
           └─ MODEL               layers (mesh) · ribbons · emitters · bones · textures · sequences
               └─ EMITTER         ~45 fields (§3.6), ten of them animated tracks
```

Four verbs apply at every level, and a control that cannot do all four for its level is a
gap: **see** it (the gizmo, the label, the readout), **set** it (the dial or the handle),
**add one from an existing spell** (never from a blank number — the game has 472 effect
models, 84 caster animations, 1,699 emitters and 312 ribbons to copy from), **remove** it.

What this changes in the tool, concretely (slices in §5): the Anatomy strip stops being a
section of the Sketch window and becomes the ROOT of the outliner; each part's row carries
its animation (by name — built today), its sound and its slots; "Composition" as a separate
section disappears into those rows; every "+" in the tree opens a picker over real spells.

Where a row is a gap, the §5 slice that closes it is named.

## 4. The task walk

"I want to …" → the click path today. **GAP** = no path; *long* = a path an author will not find.

| Intent | Path today |
|---|---|
| start a spell from nothing | New spell (above search) → Anatomy preset |
| start from Fireball and change it | search → the spell → tree |
| decide which parts it has | Anatomy ticks / presets |
| make the caster swing two-handed / cast one-handed / roar | **Anatomy row → "body does" → picker by name (today)** |
| see what an animation looks like before choosing | hover a row in the picker (today) |
| make the whole effect red | model Hue (particles/ribbons) + Tint per image (now works on white art) — *long*; a one-click "colour this part" over all three is slice C |
| make a sketch piece red | LOOK card, or PIECE COLOURS in the inspector (today) |
| make it bigger | Composition scale (kit-level) or Size dial (particles) — two dials for one intent; a scale HANDLE is slice F |
| make it last longer | Duration dial (particles) — the model's own sequence length is **not editable** (slice G) |
| start it at the hand instead of the chest | Composition: clear Chest, pick into Right hand — *long*; a slot drag in the tree is slice C |
| move an emitter's origin | translate handle / Local position |
| point an emitter the other way | rotate its bone (rings) / negative speed — explained in SPELL_CREATOR_IDE §1, still the least obvious thing in the tool |
| add sparks like Fireball's to my effect | +Em clones an emitter of THIS model only; copying an emitter FROM ANOTHER SPELL is **GAP** (slice C; S5 for sketches) |
| add a trail to my missile | the missile model's own ribbons only; a ribbon from another model is **GAP** (slice C) |
| give it a ground ring at impact | pick an impact model with one — no "ground-anchored" filter in the picker (slice C) |
| make it a projectile | Anatomy: tick Missile, then pick a missile model; speed in Composition/Completer |
| make the missile hit the head instead of the chest | **GAP** (SpellVisual f9, slice D) |
| shake the camera on impact | **GAP** (engine + kit f14, slice E) |
| tint the TARGET blue while the aura is on | **GAP** (CharProc type 1 — the most common proc in the game, engine first) |
| edit the ramp of an emitter's rate over time | first key or flatten only — **GAP** (slice A) |
| change when a burst fires | **GAP** (enable track, slice A) |
| play a sound the game already has | import own file only — **GAP** for picking an existing SoundEntries row (slice C) |
| keep my sketch for tomorrow | Session → Add to session / Push; later "open" on the saved entry (2026-10-25) |
| know that what I see is what the Completer will build | **GAP** (the round trip, slice R) |

## 6. What landed on 2026-09-19, and how it was found

Probe first (AGENTS.md rule 8): the client's `msui-console.log` from the owner's own
session answered all three reports before any code was read.

1. **"My animation is still the base spell's animation."** Every cast verdict in the log
   read `authored=57 requested=57 played=57`: the animation was never changed, because the
   only control was a raw AnimationData id in an `InputInt` under Composition — with the
   common ids mislabelled in its tooltip. Built: `Formats/AnimationDataCatalog.cs`
   (AnimationData.dbc by name), `CharacterRenderer.AvailableAnimationIds` (what this body's
   model can actually play), and `GameLoop/CreatorMode/GameLoop.Creator.AnimationPicker.cs`:
   a picker by name, split into "on this body's model" and "not on this model", hover to
   perform, click to keep, "none" and "what the source authored" pinned at the top. It sits
   on each part's row in Anatomy ("body does …") and replaces the InputInt in Composition.
   It writes the same `CreatorStageComposition.AnimationId`, so preview and export are
   unchanged.
2. **"Unable to change the tint/colour of a sketch shape."** The log showed 234 per-frame
   `override cleared for sketch_cast.m2` lines over six seconds: the owner was dragging the
   model inspector's **Tint** swatch on the sketch's image. Two defects: (a) the hue-map law
   (`Formats/BlpRecolor.cs`) preserves lightness, and at lightness 1 HSL has no room for a
   hue, so a pure-white image — every sketch image, and every white glow in the game — came
   out white whatever the target; greys and whites now MULTIPLY by the target (white → the
   colour, black stays black) and coloured pixels keep hue-mapping. (b) `RebuildCreatorModel`
   ran once per frame while the swatch moved and, finding no byte patch, cleared the effect
   override — for a sketch model, whose "original" IS the compiled bytes. A tint drag no
   longer rebuilds the model at all (it lives in the texture layer), and a sketch model
   keeps its bytes. And the inspector now carries PIECE COLOURS (the LOOK colour and alpha
   per piece) and hides Hue/Tint for a sketch's own white images.
3. **"Dragging draws line things; clicking draws full circles."** The draw canvas
   (`GameLoop.Creator.DrawCanvas.cs`) previewed a stroke as ImGui thick `AddLine` segments —
   bare rectangles, no caps, no joins — while the rasterizer (Skia, round cap + round join)
   makes one continuous band; and it stopped sampling when the cursor left the paper mid-
   drag. The preview now draws a disc at every vertex under the segments (a round join),
   and samples while the button is held.

Verification: Debug and Release builds; `spell-emitter-lab` 37,556 checks, 0 mismatches
(seven new: the tint law — white → target, grey → half target with alpha kept, black stays,
saturated pixels hue-map, a grey target is a no-op — on both the BGRA and the colour-track paths);
`interface-wire-check --shared-docs-only` and `--imgui-policy-only` green. Live: none —
the owner launches. Expected live: Cleave → Anatomy → Cast row → "body does 57 Special1H"
→ pick 18 Attack2H → the body swings two-handed on the next loop; a sketch piece → model
inspector → PIECE COLOURS swatch → the piece recolours; Tint on any white glow image now
colours it; Draw → drag a curve → a smooth band.

  it gets code.
